# Hydrus Pocket — Goal-Mode Product Delivery Scope

## Mission

Build and ship a production-ready, phone-first PWA for privately searching, browsing, viewing, and organizing a mixed-media Hydrus archive over Tailscale.

The application runs on the user’s home desktop alongside Hydrus. The primary client is an Android phone, with a responsive desktop browser experience as a secondary target.

The product must make a large personal media archive feel fast and accessible:

> Open the app, search by tags or metadata, refine and sort results, browse thumbnails, open any supported media, and make basic tag changes without using the Hydrus desktop interface.

The archive contains mixed media, not only photographs. Search accuracy, filtering, sorting, and mobile usability are the highest priorities.

---

# 1. Goal-mode operating contract

Codex owns the complete delivery lifecycle:

1. Inspect the repository and runtime environment.
2. Validate the Hydrus API and Tailscale assumptions.
3. Design the implementation.
4. Build all required product functionality.
5. Add automated tests.
6. Test against the real Hydrus instance where available.
7. Resolve defects and usability problems.
8. Harden security, error handling, and performance.
9. Produce deployment and maintenance tooling.
10. Verify the production-readiness checklist.
11. Deliver a release candidate with complete documentation.

Codex must not stop merely because an internal milestone is complete.

It should continue until the definition of done is satisfied or it reaches a genuine external blocker such as:

* Required credentials are unavailable.
* Hydrus cannot be accessed from the development environment.
* A necessary operating-system permission requires manual approval.
* Required hardware is unavailable.
* A product decision has multiple materially different outcomes that cannot be safely inferred.

For ordinary implementation ambiguity, Codex should choose the simplest robust option, document the decision, and continue.

## Working rules

* Do not leave mock data in production paths.
* Do not mark placeholder UI as complete.
* Do not defer essential error states.
* Do not disable failing tests to pass a release gate.
* Do not silently reduce the agreed feature scope.
* Do not expose the Hydrus API key to the browser.
* Do not expose Hydrus or the application publicly.
* Do not require router port forwarding.
* Do not recreate the full Hydrus desktop client.
* Prefer stable, maintainable dependencies over experimental libraries.
* Keep the implementation usable on a mid-range Android phone.
* Test functionality against real Hydrus responses, not only fixtures.
* Continue fixing discovered defects until release gates pass.

# 3. Required architecture

Use a same-origin application architecture.

```text
Android phone or laptop
        │
        │ HTTPS inside the tailnet
        ▼
Tailscale Serve
        │
        ▼
Hydrus Pocket gateway
        ├── Serves the PWA
        ├── Owns Hydrus credentials
        ├── Exposes a typed application API
        ├── Proxies thumbnails
        ├── Streams original media
        └── Preserves HTTP Range requests
                  │
                  ▼
Hydrus Client API on localhost
```

## Security boundaries

* Hydrus should remain bound to localhost where practical.
* The permanent Hydrus access key is stored only on the desktop.
* The browser must never receive the permanent access key.
* Browser storage may contain preferences and cached search data, but not Hydrus credentials.
* All remote access occurs through Tailscale.
* The application is not exposed to the public internet.
* The gateway must not function as an unrestricted generic proxy.
* Logs must redact access keys, session keys, and sensitive request headers.

## Recommended stack

### Web application

* React.
* TypeScript.
* Vite.
* React Router.
* TanStack Query or an equivalent request-state layer.
* A virtualized grid implementation.
* Service worker and web app manifest.
* Responsive CSS with mobile-first layout.

### Gateway

* Node.js.
* TypeScript.
* Fastify or another small, well-maintained HTTP framework.
* Schema-validated routes.
* Streaming responses for thumbnails and originals.
* Proper Range request forwarding.
* Structured, redacted logging.
* Health and readiness endpoints.

Codex may substitute components when it has a documented technical reason, but it must preserve the architecture and security properties.

* Debounced requests.

* Namespace visually separated from the tag value.
* Search counts aligned for quick scanning.
* Correct handling of Hydrus sibling/display tags.
* No keyboard layout jumps while suggestions load.
* Touch targets suitable for one-handed use.

## 4.6 Result handling

Hydrus search results may contain very large lists of file IDs. The application must avoid attempting to render or load an entire large archive at once.

Required behavior:

* Apply a safe default result limit.
* Tell the user when results are limited.
* Allow the limit to be increased deliberately.
* Retrieve metadata in bounded batches.
* Fetch ahead of the scroll position.
* Cancel obsolete metadata requests.
* Virtualize off-screen rows.
* Avoid duplicate metadata requests.
* Retain successfully loaded metadata during temporary network failures.
* Preserve stable result ordering.
* Restore scroll position after returning from the viewer.

Suggested defaults:

* Initial search limit: 500.
* Metadata batch: 128–256.
* Grid density: three columns in portrait mode.

These values should be configurable and validated against the real archive.
